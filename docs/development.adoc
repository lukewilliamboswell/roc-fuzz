= Contributing to roc-fuzz

The platform has four layers:

* `platform/Fuzz.roc` defines typed generators, record-builder
composition, and statically dispatched target construction.
* `platform/Target.roc` erases the app's input type behind closures.
* `platform/main.roc` exposes the byte-oriented native boundary and
declares the x64-musl and Apple Silicon macOS targets.
* `src/main.zig` adapts generated Roc ABI calls to libFuzzer and
translates the friendly runner commands.

`src/roc_platform_abi.zig` is generated from Roc's `ZigGlue.roc`.

== Toolchain

Normal documentation, Roc source validation, target builds, and
packaging require only:

* stable Roc for the repository's typed tooling; and
* the nightly Roc compiler selected by the platform and application headers.

Linker inputs have an independent, content-addressed release cycle;
`libhost.a` is deliberately outside that cycle and is built with each platform
update. This separation means a host or Roc source change does not rebuild large,
stable runtime inputs. Source development and the explicitly dispatched producer
require Zig 0.16.0. The builder uses `zig ar`.

Exact project compiler versions live in the platform and application header
`roc` fields. The shared updater changes only those pins, preserving published
URLs. Repository scripts use `ROC_STABLE` and `ROC_NIGHTLY` when set, then fall
back to the `roc-stable` and `roc-nightly` commands installed by
`lukewilliamboswell/setup-roc`.

== Generate platform inputs

Generate the current host's ignored inputs with:

[source,sh]
----
scripts/build_platform.roc
----

Pass `--target x64musl` or `--target arm64mac` explicitly in automation.
The default restores the archives selected by `native-libraries.lock.json`,
rehashes their manifest and target archive even on a cache hit, validates the
complete archive inventory, builds the current host, and writes local
`SHA256SUMS`. The archive digest is the reviewed authorization for routine use;
the cache key only locates likely bytes. This is why cache hits are still hashed
and why a cache miss downloads the exact locked release rather than rebuilding.
It avoids repeat network traffic without allowing a poisoned or truncated cache
entry to become trusted. Routine restoration does not query GitHub's attestation
service. Never commit generated archives, objects, or manifests.

The one-time rollout uses two pull requests. First merge the consumer, producer,
publisher, and temporary empty-lock handling. This infrastructure PR may use the
explicit bootstrap branch because no trusted publisher exists on the default
branch yet. Then open a same-repository adoption PR, dispatch `Publish linker
inputs` with that PR number, and review the publisher's GitHub-signed lock-only
commit. Replacing the empty lock makes routine jobs take only the locked consumer
path. This ordering keeps
release credentials in already-reviewed default-branch code while still binding
the first release to the exact adoption-PR producer commit.

The workflow-dispatch-only `Linker inputs` producer packages both targets without
`libhost.a`, tests each candidate through a fresh host and final bundle, emits a
canonical aggregate manifest, and attests that manifest and both archives. It has
no publication authority. Release new inputs for changes to their sources,
runtimes/toolchains, flags, targets, security fixes, or the macOS adapter compiled
into `libfuzzer.a`. The macOS coverage shim stays with `libhost.a`.

`Publish linker inputs` runs trusted controller code pinned to a reviewed full
`roc-automation` commit. It dispatches the producer at the exact same-repository
PR head, verifies the workflow/ref/SHA, hashes and attestations, publishes an
immutable release named from the aggregate manifest hash, and adds only the lock
in a lease-guarded GitHub-signed commit. Candidate code cannot publish, while the
privileged job never executes candidate code. The PR-built release remains the
permanent dependency after merge; rebuilding it would break the evidence-to-byte
identity that the review admitted.

GitHub immutable releases must be enabled before the first publication. The
controller checks the resulting release state and refuses to adopt a lock when
the hosting policy does not enforce immutability; a content-derived name alone
cannot prevent an administrator from replacing assets.

Before adopting a release, review its producer changes, exact source revision,
input fingerprint, manifest and archive digests, sizes, target coverage, native
link tests, and workflow attestations. Merge with a merge commit so the attested
producer SHA and signed lock commit remain reachable. Ordinary PRs and nightly
updates then know only the reviewed lock, cache, verifier, and target files; they
never dispatch or reproduce linker inputs.

The fully static build excludes `FuzzerInterceptors.cpp`. Its wrappers
locate libc functions through `dlsym`, which is not usable in the static
musl executable. The standard libFuzzer scheduler, mutators, corpus
engine, crash handling, minimizer, and merge engine remain unchanged.
Roc's compare and switch instrumentation still supplies value feedback.

The macOS target includes `FuzzerInterceptors.cpp`: its `dlsym` lookups
work with macOS's dynamic `libSystem`. Its deployment target is macOS
11.0, and its only allowed dynamic dependencies are system libraries.

`src/macos_sancov.c` supplies the public TLS slot required by Roc's
macOS stack-depth coverage instrumentation.
`src/macos_fuzzer_ext_functions.cpp` binds the standalone runner hooks
directly because upstream libFuzzer's Darwin `dlsym` lookup requires
`-export_dynamic`, which Roc does not pass. Both files are
repository-owned platform glue covered by the project license; the
native build, `show`/replay, fuzz, failure-artifact, and packaged-bundle
smoke tests exercise them on Apple Silicon.

== Regenerate ABI glue

Regenerate glue only when the Roc natural ABI changes:

[source,sh]
----
export ROC_NIGHTLY="$HOME/roc_nightly-linux_x86_64-2026-09-19-d025939/roc"
scripts/build_platform.roc -- --regenerate-glue
----

Review the generated Zig diff and rebuild every example after
regeneration.

== Validation

Every bug fix and significant new behavior should include an automated test at
the narrowest useful layer. Changes to public behavior also update the relevant
examples, interface documentation, or report schema. A pull request should
explain the behavior changed and the validation performed.

Use the compiler under development through `ROC_NIGHTLY`:

[source,sh]
----
export ROC_NIGHTLY=/path/to/roc
scripts/test_targets.roc -- --operation check --verbose
scripts/test_targets.roc -- --operation build --verbose
scripts/test_targets.roc -- --operation seed
scripts/test_targets.roc -- --operation fuzz --max-total-time 2
----

`check_all.roc` prepares the current host inputs and validates the working-tree
platform and every example. `test_targets.roc` provides the focused operations
shown above.
Checked-in example declarations remain pinned to a published release,
while local and CI runs exercise unreleased platform changes. Validation
checks the exact example inventory, Roc formatting and types. After
generating the current host inputs, building creates every
self-contained executable and verifies a static x86-64 ELF on Linux or
an arm64 Mach-O with system-only dynamic dependencies on macOS. Seed
validation renders and replays each deterministic input. The fuzz
operation runs short campaigns and verifies that an intentional Roc
failure is saved byte-for-byte with follow-up commands.

Build the HTML manual, PDF, and generated API reference with:

[source,sh]
----
scripts/build_docs.roc
----

The command fetches the immutable shared renderer from `roc-automation`, uses
Docker for the Asciidoctor toolchain, and writes the complete publication under
`.docs-out/`. Set `ROC_AUTOMATION_ROOT` to a local checkout while developing the
shared action. The final API audit fails if an exposed module or public entry
has no rendered documentation. The documentation and release workflows run the
same build and audit.

Every example runs the `check`, `test`, `build`, `seed`, and `fuzz`
stages by default. A temporary exception must use a `skip` entry in
`tests/targets.json` with both a concrete reason and a full GitHub issue
URL. The driver rejects unexplained skips; skipping a prerequisite also
requires skipping its dependent stages.

CI has two explicit lanes: public downloads use committed URLs on fresh
runners, and development tests use the working-tree bundle. Both run on
every PR and manual/nightly dispatch; there is no change classifier or
migration exception. The release workflow additionally tests the exact
candidate archives. `nightly_validation: true` never publishes or
deploys.

Linux CI also rebuilds the checksum-pinned libFuzzer sources with
AddressSanitizer and runs a short native smoke campaign. This detects heap,
stack, use-after-free, and leak errors in the embedded C++ fuzzing engine on
every pull request, every `trunk` update, and before release publication. Run
the same check locally with
`roc-stable --opt=dev scripts/test_native_sanitizers.roc`; it requires Clang,
`curl`, and `tar`. The sanitizer executable is CI-only and does not change the
static release artifacts.

When checking, testing, or building with a newer compiler, the runner
permits Roc's warning-only exit code only if every diagnostic is a
compiler-pin mismatch. The warnings remain visible. Errors, other
warnings, and runtime failures still fail validation; published URLs and
downloaded compiler pins are never rewritten.

Every target asserts on allocation behaviour as well as on results. A
property can check what an operation computes but not what it costs, so
a builtin that stops mutating a uniquely owned value in place and starts
copying it still returns the right answer and no content property
notices. Pin the cost with `Fuzz.expect_allocs_at_most!` or
`Fuzz.expect_allocs_at_least!`, and build the target with
`Fuzz.target_with!` or `Fuzz.from_bytes!` so the property may perform
effects. The `check` stage requires one of those assertion helpers; raw
counter reads, measurements, and leak-only checks do not satisfy the
policy. A target that genuinely cannot assert on cost belongs in
the allocation-assertion exemptions in `scripts/test_targets.roc` with a concrete
reason.

Assert on a difference between two counter reads, never on a raw value:
the counter is process-wide and libFuzzer reuses one process across
millions of inputs. Only assert zero for a value that is uniquely owned
and pre-sized, because copy-on-write allocation is correct when a value
is aliased.

Separately, the runner checks after every input that the target freed
everything it allocated, and fails the input otherwise. Pass
`--no-detect-leaks` to a run to turn that off.

The former byte-oriented builtin targets live under `examples/builtins/`
and use `Fuzz.from_bytes`. This keeps their existing properties in the
regression matrix. Top-level examples are an end-user gallery and should
prefer `Fuzz.target`, typed generators, and the `.Fuzz` record builder.
A multi-file example must live in its own directory with `main.roc` as
its app root; the test driver enforces this so editor tooling can
discover the project naturally.

== Release bundle

Create a Roc platform bundle after generating both target input sets
with:

[source,sh]
----
scripts/build_bundle.roc -- --output-dir dist
----

`build_bundle.roc` verifies every generated input checksum, then includes the
archives and license notices in
`roc bundle`. Production release jobs build both hosts on native hosted
runners before bundling. Test the resulting bundle from an external
target with:

[source,sh]
----
scripts/test_bundle.roc -- dist/<bundle>.tar.zst
----

Production releases use the `Release` workflow. From the repository's
*Actions* tab, run it on the default branch with an `X.Y.Z` version (or
an `X.Y.Z-rcN` release candidate). Pull requests run the same workflow
in dry-run mode. Before dispatching any publication, add a non-empty
`docs/releases/X.Y.Z.adoc` or `docs/releases/X.Y.Z-rcN.adoc`. The first heading
must be `= roc-fuzz VERSION`. Release notes are reviewed as documentation and
should explain the release to users: lead with the theme, show notable features
and compatibility changes, name the supported hosts and Roc compiler, link to
verification material, and give upgrade or feedback guidance.

Use `{platform-url}` where the copyable app header needs the content-addressed
bundle URL and `{manual-url}` for the release's PDF. The workflow resolves both
after packaging, translates the note's headings and source blocks to GitHub
Markdown with `scripts/render_release_notes.roc`, and uses that result as the
description for stable releases and release candidates. A missing or mismatched
note stops publication. A real release:

[arabic]
. validates all sources, tests, and short fuzz campaigns;
. builds the platform bundle and tests that packaged bundle as an
external consumer;
. generates and validates a version-stamped PDF manual and HTML site containing
the API reference; and
. renders the matching narrative release note and publishes it with the bundle,
PDF, zipped documentation site, SBOM, and provenance in a GitHub release.

Pages is independent of a release and always tracks `trunk`. Pull requests build
the same site without deploying it.

The bump check requires a version increment from the previous platform
release. The release policy explicitly permits exact-nightly bootstrap
on `trunk`; no stable compiler compatibility or maintenance branch is
implied.

To unblock a source PR before stable bootstrap, dispatch `Release` on
that branch with `release_candidate=true`, a new `X.Y.Z-rcN` version,
and the full source SHA in `expected_sha`. Both target bundles must pass
before the workflow attests and publishes the RC. Only this explicit RC
path permits source-built libraries. It preserves the latest stable
release and the trunk-tracking Pages site, and does not create a default-branch URL follow-up.
Verify the published archive and adopt its URL in the originating PR.
Stable releases still require the independent library lock.

URL follow-ups are a maintainer task, not another release workflow:

[arabic]
. Download the published archive, compare its digest with the tested
artifact, and verify its attestation with
`gh attestation verify --repo lukewilliamboswell/roc-fuzz --signer-workflow lukewilliamboswell/roc-fuzz/.github/workflows/release.yml <archive>`.
. Update the example and README platform URLs without changing compiler
pins. Commit with a verified signature and open a reviewed PR.
. Require current-head CI (including Linux/macOS public-download tests)
before merging. If workflows do not start automatically, dispatch CI on
that branch with `nightly_validation=true` and check that branch
protection accepts it.

If new examples need unpublished APIs, use a tested RC and adopt its URL
before merging. The nightly updater remains pin-only and must not repair
release URLs. Inspect partial publication before recovery; never replace
existing tags or assets or rebuild an already-published release from a
moving branch. Preserve the run's exact tested artifacts and inspect the
tag SHA and uploaded digests before recovery; do not blindly rerun a
publishing job.

After an interrupted URL follow-up, resume the existing reviewed PR and
rerun validation on its current head; do not create a duplicate PR or
republish assets.

== Design constraints

Static dispatch happens while `Fuzz.target` is specialized for the app's
input type. `Target` then erases that type, preventing the native ABI
from depending on every app record or tag-union layout.

The platform supports x64-musl and Apple Silicon macOS. Keep native
calls behind generated glue so compiler ABI changes are caught by
regeneration and compilation.
