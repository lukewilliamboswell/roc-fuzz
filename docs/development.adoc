= Contributing to roc-fuzz

The platform has four layers:

* `platform/Fuzz.roc` defines typed generators, record-builder
composition, and statically dispatched target construction.
* `platform/Target.roc` erases the app's input type behind closures.
* `platform/main.roc` exposes the byte-oriented native boundary and
declares the x64-musl and Apple Silicon macOS targets.
* `src/main.zig` adapts generated Roc ABI calls to libFuzzer and
translates the friendly runner commands.

`src/roc_platform_abi.zig` is generated from Roc's `ZigGlue.roc`.

== Toolchain

roc-fuzz follows the
https://lukewilliamboswell.github.io/roc-automation/[roc-automation manual].
Two Roc compilers are involved, and they are not interchangeable:

* `roc-stable` runs the scripts under `scripts/` and nothing else. It is one
  nightly release, named in `Blueprint.roc` and repeated in the `roc` field of
  every script header. It changes only through a reviewed pull request.
* `roc` checks, tests, builds and bundles the platform and every application
  that depends on it. It is the latest published nightly and is not pinned
  anywhere: the platform, the examples and the test targets carry no `roc`
  field. Users install the newest compiler, so that is the one the platform has
  to work with.

`Blueprint.roc` declares the tooling environment and `Blueprint.lock` pins it:
`roc-stable`, the Roc bundles the scripts depend on, and the programs they
start. https://github.com/lukewilliamboswell/roc-blueprint[roc-blueprint]
realises that environment with Nix, the same way on a contributor's machine and
on every CI runner. To work on roc-fuzz you need:

* https://nixos.org/download[Nix];
* the `blueprint` command, from the roc-blueprint release that the platform URL
  in `Blueprint.roc` names: `nix profile install github:lukewilliamboswell/roc-blueprint/VERSION`,
  or the release's prebuilt binary checked against its published SHA-256;
* a current Roc nightly installed as `roc`.

The environment supplies Zig 0.16.0, from
https://github.com/mitchellh/zig-overlay[zig-overlay], to build the host and its
linker inputs and to format the host bindings. `scripts/native-deps.json` names
the same version, and the supply-chain check holds the two together.

[source,sh]
----
blueprint tasks          # list the declared tasks
blueprint run check      # everything a pull request must pass that needs no host
blueprint shell          # enter the environment and run scripts/*.roc directly
----

Run `blueprint` from an ordinary shell. Inside the environment `roc-stable` is
the pinned compiler and your own `roc` remains visible. Arguments to a
task follow `--`, for example `+blueprint run build-platform -- --target x64musl+`.

Linker inputs have an independent, content-addressed release cycle;
`libhost.a` is deliberately outside that cycle and is built with each platform
update. This separation means a host or Roc source change does not rebuild large,
stable runtime inputs. The builder uses `zig ar`.

Repository examples use relative paths to the working-tree platform. Each
release provides `roc-fuzz-examples-VERSION.zip` with complete applications,
supporting modules, the cases that describe them, and that release's exact
platform URL. Nothing else in an archived example differs from the repository.
The `Nightly compatibility` workflow runs the latest release's archive, exactly
as published, on the latest nightly every day.

=== Maintain the tooling

Nothing updates the tooling on a schedule. Each of these is a pull request a
maintainer opens:

Update the lock:: Run `blueprint update`, or `blueprint update INPUT` to move
one input, then `blueprint run check`.
Change the tooling compiler:: Change the tag in `Command("roc-stable", ...)` in
`Blueprint.roc` and the `roc` field of every script to the same tag. The check
script fails until they match. Run `blueprint update roc` if the locked overlay
predates that nightly.
Upgrade Blueprint:: Change the platform URL in the `Blueprint.roc` header, run
`blueprint check` and then a full `blueprint update`, and review the new lock.
No workflow names the version: `actions/setup-blueprint` reads it from
`Blueprint.roc` and verifies the binary against the checksums roc-automation
records, so a release it does not record yet needs that action repinned first.
Update a script dependency:: Change the release URL in each script header and
under `RocPackages` in `Blueprint.roc`, adding any new dependency of that
dependency (`roc-stable deps scripts/check_all.roc` lists them), then run
`blueprint update`.
Keep the SBOM composition current:: `sbom/composition.json` gives every input
`Blueprint.roc` declares (each source, tool, fetched program, script package
and task) a disposition. A new task or tool needs an entry there too, or the
release dry run's SBOM step refuses the composition. A change to what the
native inputs contain, such as a new library or a new Zig release, changes its
components.
Regenerate the host bindings:: See <<host-bindings>>.

== Repository scripting convention

Repository-owned automation is written in Roc. Put executable entry points in
`scripts/*.roc` and reusable logic in `scripts/src/*.roc`. Use the existing shared
modules for commands, paths, hashing, source edits, archives, and release metadata.
Do not add Python scripts, shell launchers, or build-before-run wrappers to work
around compiler behavior. Keep workflow YAML limited to job orchestration and
small environment/output plumbing; substantive automation belongs in Roc.

Every entry point starts with the `#!/usr/bin/env roc-stable` shebang, is
committed as executable, and is declared as a `Task` in `Blueprint.roc`. CI
calls tasks, never script paths, so a workflow and a contributor run the same
command. A script starts another script through `Script.roc_stable!` and runs
package work through `Script.roc!`, which is the `roc` on `PATH`. Never use
`roc-stable` to check, test or bundle the platform. A successful script must
return zero, and a failed script must remain a failure.

A script references every dependency by immutable release URL, and the same URL
is listed under `RocPackages` in `Blueprint.roc`. `scripts/check_supply_chain.roc`
holds each header to `Blueprint.roc`: the shebang, the `roc` field, and every
bundle URL. It also fails when a Roc file outside `scripts/` carries a `roc`
field, and when a workflow references an action by anything but a full commit
SHA.

Roc scripts may invoke standard tools such as Git, curl, tar, zip, and unzip via
argument lists, without shell evaluation. Roc owns selection, validation, and
control flow. Declare a program a script starts under `Tools` in `Blueprint.roc`.
Pinned external tools and shared actions remain external dependencies;
for example, the shared documentation builder currently uses Python internally.
That does not justify adding repository-owned Python orchestration.

Pure regression checks belong in shared-module `expect`s imported by
`scripts/tooling_tests.roc`. Filesystem and process checks belong in
`scripts/tooling_integration_tests.roc`; both run from `scripts/check_all.roc`.

== Generate platform inputs

Generate the current host's ignored inputs with:

[source,sh]
----
blueprint run build-platform
----

Pass `+-- --target x64musl+` or `+-- --target arm64mac+` explicitly in automation.
The default restores the archives selected by `native-libraries.lock.json`,
rehashes their manifest and target archive even on a cache hit, validates the
complete archive inventory, builds the current host, and writes local
`SHA256SUMS`. The archive digest is the reviewed authorization for routine use;
the cache key only locates likely bytes. This is why cache hits are still hashed
and why a cache miss downloads the exact locked release rather than rebuilding.
It avoids repeat network traffic without allowing a poisoned or truncated cache
entry to become trusted. Routine restoration does not query GitHub's attestation
service. Never commit generated archives, objects, or manifests.

The `Linker inputs` producer, `link-inputs.yml`, runs on a pull request that
touches the recipe and on dispatch. One Linux job cross-compiles both targets,
and a job on each target runs every case against the candidate. It packages both targets without
`libhost.a`, tests each candidate through a fresh host and final bundle, emits a
canonical aggregate manifest, and attests that manifest and both archives. It has
no publication authority. Release new inputs for changes to their sources,
runtimes/toolchains, flags, targets, security fixes, or the macOS adapter compiled
into `libfuzzer.a`. The macOS coverage shim stays with `libhost.a`.

`Publish link inputs` runs trusted controller code pinned to a reviewed full
`roc-automation` commit. It dispatches the producer at the exact same-repository
PR head, verifies the workflow/ref/SHA, hashes and attestations, publishes an
immutable release named from the aggregate manifest hash, and adds only the lock
in a lease-guarded GitHub-signed commit. Candidate code cannot publish, while the
privileged job never executes candidate code. The PR-built release remains the
permanent dependency after merge; rebuilding it would break the evidence-to-byte
identity that the review admitted.

GitHub immutable releases must be enabled before the first publication. The
controller checks the resulting release state and refuses to adopt a lock when
the hosting policy does not enforce immutability; a content-derived name alone
cannot prevent an administrator from replacing assets.

Before adopting a release, review its producer changes, exact source revision,
input fingerprint, manifest and archive digests, sizes, target coverage, native
link tests, and workflow attestations. Merge with a merge commit so the attested
producer SHA and signed lock commit remain reachable. Ordinary pull requests
then know only the reviewed lock, cache, verifier, and target files; they
never dispatch or reproduce linker inputs.

The libraries are byte-reproducible: the same sources, Zig release and flags
give the same bytes on any machine, in any directory, at any time. Nothing is
compiled with debug information, which would record the absolute paths of the
Zig installation, its cache and the working directory, and archive members are
named by file name alone where Zig names them by cache path. The macOS target
is compiled against the headers Zig bundles, so it builds on Linux as well as on
macOS and reads no installed Apple SDK. Keep it that way: a change that makes
two builds of the same commit differ is a defect in the recipe.

A routine pull request never rebuilds the libraries. It hashes a short list of
files and compares the result with the `input_fingerprint` the lock records;
`LinkInputs.fingerprint_inputs` is the list:

* `scripts/native-deps.json`: the Zig release, the libFuzzer source, and the
  recipe revision;
* the macOS libFuzzer adapter and the stand-in header it is compiled with; and
* the licence files packed beside the libraries.

No script, workflow or lock file is in it, so editing tooling never demands a
release. The recipe itself lives in scripts, and that is what the recipe
revision is for: raise `recipe_revision` when a change to the build alters a
library byte, such as a flag, a target or the list of libraries.

Reproducibility keeps that honest, and three checks guard it:

* The `Linker-input recipe` job of `ci.yml` is part of `CI required`. It asks
  whether the pull request touches the recipe, which is the list in
  `LinkInputs.recipe_paths`: the build script, the target definitions, the
  recipe file, the macOS sources, and `Blueprint.roc` and `Blueprint.lock`,
  which supply Zig. A routine pull request stops there. One that touches the
  recipe rebuilds both targets and, while the lock claims to be current,
  requires the result to be byte-identical to the locked release. A change that
  alters a library without raising the revision fails, naming the files, and
  cannot merge. So does a change that makes the build irreproducible.
* The `Linker inputs` producer makes the same comparison when it builds a
  candidate, and runs every case against it on both targets.
* The supply-chain check fails when a path in `LinkInputs.recipe_paths` is
  missing from the producer's `paths` filter, so a file added to the recipe
  cannot be left out of the trigger.

Run the comparison locally with:

[source,sh]
----
blueprint run build-platform -- --target x64musl --target arm64mac --libraries source --libraries-only
blueprint run link-inputs -- --operation check-source
----

When the fingerprint changes, or that comparison fails, use this sequence:

. Stage the change in a same-repository PR, raising `recipe_revision` if the
  build recipe changed. Its `Platform bundle` job fails with a stale-lock error
  until the new lock is adopted.
. To inspect a nonpublishing candidate, dispatch `Linker inputs` on the PR branch
  with `release_candidate=true` and `expected_sha` set to its exact current head.
  For example, run `gh workflow run link-inputs.yml --ref BRANCH -f release_candidate=true -f expected_sha=SHA`, replacing `BRANCH` and `SHA`.
  Review both target tests, the manifest, archive hashes, and attestations. This
  run does not create a GitHub release or edit the PR.
. From `trunk`, dispatch `Publish link inputs` with `pull-request` set to that
  PR number: `gh workflow run publish-link-inputs.yml --ref trunk -f pull-request=NUMBER`.
  To recover an interrupted publication, also pass `producer-run` with the ID of
  the successful producer run for the current head.
  The trusted publisher reruns the producer at the exact PR head,
  publishes the immutable linker-input release, and appends a GitHub-signed
  `native-libraries.lock.json`-only commit to the PR. Do not dispatch it from
  the PR branch or rebuild the inputs after merging.
. Review that lock commit and revalidate the updated PR. After its required
  checks pass, merge the PR with a merge commit. Publish a new Roc platform
  bundle later through the separate `Release` workflow, using the adopted lock.

The optional preview in step 2 does not replace the producer run performed by
the trusted publisher in step 3. The publisher is the release operation; stop
before that dispatch when only candidate validation is authorized.

The fully static build excludes `FuzzerInterceptors.cpp`. Its wrappers
locate libc functions through `dlsym`, which is not usable in the static
musl executable. The standard libFuzzer scheduler, mutators, corpus
engine, crash handling, minimizer, and merge engine remain unchanged.
Roc's compare and switch instrumentation still supplies value feedback.

The macOS target includes `FuzzerInterceptors.cpp`: its `dlsym` lookups
work with macOS's dynamic `libSystem`. Its deployment target is macOS
11.0, and its only allowed dynamic dependencies are system libraries.

`src/macos_sancov.c` supplies the public TLS slot required by Roc's
macOS stack-depth coverage instrumentation.
`src/macos_fuzzer_ext_functions.cpp` binds the standalone runner hooks
directly because upstream libFuzzer's Darwin `dlsym` lookup requires
`-export_dynamic`, which Roc does not pass. Both files are
repository-owned platform glue covered by the project license; the
native build, `show`/replay, fuzz, failure-artifact, and packaged-bundle
smoke tests exercise them on Apple Silicon.

== Host bindings

The host is compiled against `src/roc_platform_abi.zig`, which `roc glue`
generates from `platform/main.roc`. The file is committed. The host build reads
it and never generates it, so the host builds the same way on every runner and
a change to the interface is reviewed as a diff.

The compiler generates the bindings, so a new nightly can change them when
nothing in this repository changed. The `Host bindings` job of `ci.yml`
regenerates them with the nightly the run resolved and fails when the committed
file differs. Run the same check locally with:

[source,sh]
----
blueprint run check-glue
----

The glue specification comes from the source archive attached to that nightly's
release, verified against the SHA-256 that GitHub records for the asset. For a
compiler built from source, name its checkout with `-- --roc-source DIR`.

When the check fails and the change did not touch `platform/`, the compiler
changed the interface. Upgrading is a manual task, because a changed layout or
signature usually needs a matching host change:

. Run `+blueprint run check-glue -- --update+` with the latest nightly as `roc`.
. Review the diff and change the host where a layout or signature changed.
. Build the host for every target and run the targets.
. Open one pull request with the bindings and the host change.

== Validation

Every bug fix and significant new behavior should include an automated test at
the narrowest useful layer. Changes to public behavior also update the relevant
examples, interface documentation, or report schema. A pull request should
explain the behavior changed and the validation performed.

The scripts use whichever `roc` comes first on `PATH`. To validate with a
compiler under development, put it there:

[source,sh]
----
PATH=/path/to/roc/zig-out/bin:$PATH blueprint run check
blueprint run test-targets -- --operation check --verbose
blueprint run test-targets -- --operation build --verbose
blueprint run test-targets -- --operation seed
blueprint run test-targets -- --operation fuzz --max-total-time 2
----

`blueprint run check` needs no native inputs: it formats, tests the scripts,
runs the pin and supply-chain checks, and type-checks the platform and every
case in `tests/targets.json`. After native inputs are prepared, `test-targets`
provides the focused operations shown above.
Checked-in examples and test targets use the local platform. The nightly
compatibility workflow uses the latest release's own archived examples and
immutable bundle. Validation
checks the exact example inventory, Roc formatting and types. After
generating the current host inputs, building creates every
self-contained executable and verifies a static x86-64 ELF on Linux or
an arm64 Mach-O with system-only dynamic dependencies on macOS. Seed
validation renders and replays each deterministic input. The fuzz
operation runs short campaigns and verifies that an intentional Roc
failure is saved byte-for-byte with follow-up commands.

Build the HTML manual, PDF, and generated API reference with:

[source,sh]
----
blueprint run docs
blueprint run site
----

`docs` runs `roc-docs`, the renderer `actions/build-docs` runs, at the
roc-automation tools release that `Blueprint.roc` names and `Blueprint.lock`
pins by digest. It writes the working tree's manual, PDF and API reference
under `.docs-out/`. `site` assembles what GitHub Pages serves: the latest
release's documentation, restored from the archive that release published, with
the working tree's under `unreleased/`.

The renderer does not run Mermaid. Each diagram's PNG is prepared once, checked
in under `docs/images/` with a provenance note saying how it was made, and
registered with its source's digest in `docs/prepared-diagrams.json`. Editing a
diagram's source fails the build until its image is prepared again. The final API audit fails if an exposed module or public entry
has no rendered documentation. The documentation and release workflows run the
same build and audit.

Every case runs the `check`, `test`, `build`, `seed`, and `fuzz`
stages by default. To switch off a case's seed replay or fuzz run, set its
`skip_seed` or `skip_fuzz` and add an entry to the `skips` list in
`tests/targets.json` with the case name, the operation, a concrete reason and a
full issue URL. The supply-chain check rejects a skip without exactly one such
note, and a note left behind once the case runs again. The driver names every
skip and its reason at the start of each run. No case is skipped today.

A file under `trophy-case/repros/` that can run is a case in
`tests/targets.json`. The one kept there is a deliberate type error that the
compiler once panicked on; `blueprint run check` requires `roc check` to report
it.

Three workflows each answer one question:

`ci.yml`:: Does this change work with today's compiler? One job runs
`blueprint run check` and audits the API reference. One job regenerates the
host bindings and compares them with the committed file. One builder
cross-compiles the host for both targets around the locked inputs and
assembles a single bundle, and a job on each
target downloads that bundle and runs every case against it. `CI required`
aggregates them.
`release.yml`:: Do these exact bytes work? On a pull request it is a dry run
under the version `0.0.1-dry-run`: it builds the bundle, the examples archive,
the SBOM, the documentation archive and the release notes, and tests the
archive against the bundle on both targets. `Release required` aggregates it.
`nightly.yml`:: Does the latest release still work with today's compiler? It
runs daily; see <<release-bundle>>.

A new nightly can fail an untouched pull request. Compare with the latest
`Nightly compatibility` run and with `trunk` before treating a failure as a
regression in the change.

Linux CI also rebuilds the checksum-pinned libFuzzer sources with
AddressSanitizer and runs a short native smoke campaign. This detects heap,
stack, use-after-free, and leak errors in the embedded C++ fuzzing engine on
every pull request, every `trunk` update, and before release publication. Run
the same check locally with
`blueprint run native-sanitizers`; it requires Clang,
`curl`, and `tar`. The sanitizer executable is CI-only and does not change the
static release artifacts.

The Roc driver runs on Linux and Apple Silicon without platform skips. Scripts
execute directly with the fixed tooling compiler; compilation errors, warnings,
and application failures retain their normal Roc exit status.

Use `--suite-root PATH` to run an unpacked examples archive containing `examples/` and
`tests/targets.json`. Each invocation has fresh temporary executables and corpora.
Fuzz smoke tests pass corpus directories to libFuzzer; passing an individual seed
file would only replay it. Repository formatting is checked separately, not against
an older release's frozen source.

Nightly compatibility selects the highest stable semantic-version platform
release, ignoring linker-input releases and release candidates. Both targets
consume the same selection and verify asset hashes. Releases through 0.4.1 use
examples from the exact tag commit, rebound to that release's own bundle (the old
manual URL follow-up could occur after tagging). Newer releases must include the
examples archive. The compatibility artifact records the release, source commit,
compiler and asset identities used; a missing archive or failed download cannot
become a passing test. Archives up to 0.4.3 pin every example to the compiler of
their day, so the driver accepts the resulting version-mismatch warning; later
archives carry no pin.

Every target asserts on allocation behaviour as well as on results. A
property can check what an operation computes but not what it costs, so
a builtin that stops mutating a uniquely owned value in place and starts
copying it still returns the right answer and no content property
notices. Pin the cost with `Fuzz.expect_allocs_at_most!` or
`Fuzz.expect_allocs_at_least!`, and build the target with
`Fuzz.target_with!` or `Fuzz.from_bytes!` so the property may perform
effects. The `check` stage requires one of those assertion helpers; raw
counter reads, measurements, and leak-only checks do not satisfy the
policy. A target that genuinely cannot assert on cost belongs in
the allocation-assertion exemptions in `scripts/test_targets.roc` with a concrete
reason.

Assert on a difference between two counter reads, never on a raw value:
the counter is process-wide and libFuzzer reuses one process across
millions of inputs. Only assert zero for a value that is uniquely owned
and pre-sized, because copy-on-write allocation is correct when a value
is aliased.

Separately, the runner checks after every input that the target freed
everything it allocated, and fails the input otherwise. Pass
`--no-detect-leaks` to a run to turn that off.

The byte-oriented builtin targets live under `tests/targets/builtins/`
and use `Fuzz.from_bytes`. They are regression tests for the compiler and its
builtins: `tests/targets.json` lists them beside the examples, pull-request CI
runs them, and a release's examples archive leaves them out. The applications
under `examples/` are an end-user gallery and should
prefer `Fuzz.target`, typed generators, and the `.Fuzz` record builder.
A multi-file example must live in its own directory with `main.roc` as
its app root; the test driver enforces this so editor tooling can
discover the project naturally.

== Release bundle

Create a Roc platform bundle after generating both target input sets
with:

[source,sh]
----
blueprint run bundle -- --output-dir dist
----

`build_bundle.roc` verifies every generated input checksum, then includes the
archives and license notices in
`roc bundle`. Test the resulting bundle from an external
target with:

[source,sh]
----
blueprint run test-bundle -- dist/<bundle>.tar.zst
----

=== What a release contains

One immutable GitHub release per version holds:

[cols="2,3",options="header"]
|===
| Asset | Purpose

| The bundle, under the filename `roc bundle` emits
| What users depend on. The filename is its content hash.

| `roc-fuzz-examples-VERSION.zip`
| The examples pinned to this release's bundle, with the cases that describe them.

| `roc-fuzz-docs-VERSION.zip`
| The manual and API reference for this version. The documentation site restores the latest release's copy.

| `roc-fuzz-VERSION.pdf`
| The manual.

| `<bundle>.spdx.json`, `<bundle>.cdx.json`
| The bundle's SBOM, as SPDX 3.0.1 and CycloneDX 1.7, written from `sbom/composition.json`.

| `<bundle>.sbom-manifest.json`
| The evidence manifest binding the bundle and its SBOM documents by digest.

| `*.intoto.jsonl`
| The exported build-provenance attestations for the bundle and the examples archive.
|===

=== Write the release notes

Before dispatching a release, commit a non-empty `docs/releases/X.Y.Z.adoc`, or
`docs/releases/X.Y.Z-rcN.adoc` for a release candidate, and add an `include`
for it at the top of `docs/releases.adoc`. The first heading
must be `= roc-fuzz VERSION`. Release notes are reviewed as documentation and
should explain the release to users: lead with the theme, show notable features
and compatibility changes, name the supported hosts, link to
verification material, and give upgrade or feedback guidance.

Use `+{platform-url}+` where the copyable application header needs the
content-addressed bundle URL, and `+{manual-url}+` for the release's PDF. Do not
put a `roc` field in that header. The build job fills both in after it has made
the bundle, translates the note's headings and source blocks to GitHub Markdown
with `scripts/render_release_notes.roc`, and appends the output of `roc version`
and `roc-stable version`. That record is the release's statement of what it was
built and tested with. Notes that never use `+{platform-url}+`, or that leave a
placeholder unresolved, fail the build.

The committed file keeps its placeholders and is never rewritten after the
release. A pull request renders every notes file newer than the latest release,
so a mistake in unreleased notes fails on the pull request that makes it.

=== Publish a release

From the repository's *Actions* tab, run `Release` on `trunk` with an `X.Y.Z`
version. The workflow:

. rejects a version whose tag or release exists, requires `trunk`, and requires
  the notes file;
. runs `blueprint run check` and the sanitizer check on that commit;
. cross-compiles the host for both targets, bundles once, and checks the requested
  version against the public API with `roc bump --expect`, so a breaking change
  cannot go out as a patch;
. builds the examples archive with the real release URL, the SBOM, the
  documentation archive, the manual and the rendered notes;
. on each target, serves the bundle on a loopback address and runs the archived
  examples against it, with an empty package cache;
. attests the tested bundle and examples archive; and
. publishes from a job that checks out nothing and runs no repository script. It
  stages a draft release at the tested commit, uploads every asset, downloads
  each one back and compares it with the tested file, and only then publishes.

After a final release the workflow rebuilds and deploys the documentation site,
which leads with the latest release.

The publish job runs in the `release` environment. Use `roc bump` before
choosing a version:

[source,sh]
----
roc bump --old <previous release bundle URL> platform/main.roc
----

A release candidate is the same dispatch with an `X.Y.Z-rcN` version. It goes
through every step above, holds the same assets, and is published as a
prerelease that is never the latest release. Nightly compatibility and the
documentation site ignore it. Fix what a candidate turns up on `trunk` and
publish `-rc2`; a candidate is immutable like any other release.

=== When a new compiler breaks the latest release

`Nightly compatibility` runs every day. It selects the latest Roc nightly and
the latest stable platform release, and runs that release's examples archive,
unchanged, on both targets with `trunk`'s scripts. Its report job keeps one
issue, titled "The latest release fails on the latest Roc nightly": opened by
the first failure, commented on by each later one, and closed by the next pass.
A run in which setup failed before any example ran fails without touching the
issue.

A release is immutable, so the fix is always a patch release that works with
the new compiler. Reproduce a past combination by dispatching the workflow with
a `nightly-tag` and a `release-version`.

=== Recover an interrupted publication

Inspect exactly what exists before retrying. An unfinished draft can be
completed from the same run's artifacts: upload what is missing, verify the
complete inventory, then publish. A published release that is incomplete cannot
be repaired; publish a new version. Changed bytes are always a new version.
Never replace an existing tag or asset, and never rebuild a release from a
moving branch.

== Design constraints

Static dispatch happens while `Fuzz.target` is specialized for the app's
input type. `Target` then erases that type, preventing the native ABI
from depending on every app record or tag-union layout.

The platform supports x64-musl and Apple Silicon macOS. Keep native
calls behind the generated bindings, so that a compiler ABI change is caught by
the bindings check and by compilation.
